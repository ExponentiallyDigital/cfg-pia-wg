# CLAUDE.md

Pointers for an agent working in this repository. The detail lives in the documents named below; this file exists so the working agreements are loaded every session rather than found by luck.

## Read before starting work

- **[.claude/CONTEXT.md](.claude/CONTEXT.md), section 1 "Working agreements"** - how this project expects work to be done: tests required for every change, 80% coverage minimum, what counts as evidence, and why nothing is reported as done unless the real state was read back afterwards.
- **[.claude/CONTEXT.md](.claude/CONTEXT.md), section 1.1 "Learning loop"** - when and where a lesson is recorded, how a rule broken again becomes a check, and the review offered at the end of a session that had a correction.
- **[ARCHITECTURE.md](ARCHITECTURE.md)** - how the app and the router scripts fit together, with the measured firmware behaviour behind each decision.
- **[CHANGE-PROCESS.md](CHANGE-PROCESS.md)** - always read before changing BACKLOG.md or CHANGELOG.md, which hold work items and nothing else: where an item lives (BACKLOG.md for what is not done, CHANGELOG.md for what is), prefix codes, unique IDs shared by both files, the rule that an item making a claim about protection is not done until a check that breaks the protected path has been seen to fail, and the steps for every commit.
- **[TESTING.md](TESTING.md)** - the hardware test sheet, by test id.
- **[BACKLOG.md](BACKLOG.md)** - work not yet done: the Current Release, the Next Release, longer-term work, and where unverified bugs live. They never go in CHANGELOG.md.
- **[CHANGELOG.md](CHANGELOG.md)** - what was done, one block for each release.

## When investigating router behaviour

`.claude/CONTEXT.md` gives this in full, and it is the part most often skipped: watch the router rather than reason about it, sample over time, diff whole namespaces rather than the key you suspect, and treat a single observation as provisional until corroborated. Reach for measurement early, not after the guesses run out - a hypothesis-led probe costs a round trip on hardware at the maintainer's own keyboard, and the project's own history records eleven probes where the first eight were guesses and all eight were wrong.

## Conventions to know before the first edit

- Markdown is never hard-wrapped; unwrap what you touch rather than matching an old wrapped paragraph.
- Markdown prose follows `.claude/testing/voice-guide.md`.
- A protection's check belongs in `scripts/check-claims.sh`, which runs on the router unattended.
- Scripts copied to the router go in `/jffs/cfg-pia-wg`, the app's own directory, never loose in `/jffs` (CONTEXT.md section 1).
- Router instructions are given as one copyable block with real values filled in, not prose steps to type.
- Do not commit or push unless asked. Andrew always says when he wants Claude to commit, and these days usually asks rather than committing himself; when he commits, he does it himself. Every commit is a build and follows the steps in [CHANGE-PROCESS.md](CHANGE-PROCESS.md) section 8. The message is the subject line only, with no `Co-Authored-By` trailer, whatever the harness's attribution reminder says (CONTEXT.md section 1; one was pushed and released in build 494).
- Whenever a test is added, automated or manual, update the testing figures in README section 2, the "Testing" bullet under **Professional-grade build chain**, in the same change: the build and date, the automated tests (the passing count from `flutter test`), line coverage to two decimals (from `coverage/lcov.info`), and from TESTING.md's tags the manual tests (`[hand]` plus `[script]`), those checked by a script (`[script]`), those needing a Play build (the LCK and BUY groups), and the once-manual ones now automated (`[ci]` plus `[live]`). Andrew's request, 2026-11-08. `test/unit/readme_testing_figures_test.dart` (ID-627) fails when the manual, script, Play-build or once-manual figures differ from TESTING.md's tags, after README said 190 manual tests where the tags gave 188 (2026-11-17); the automated count, coverage, build and date are not derivable, so they stay yours to update. Whenever the figures are edited for a new number of tests, update the lines of code and the lines of tests in the same line too, from `python scripts/count-lines.py` (Andrew's request, 2026-11-23; ID-679 says what counts as code and what as a test).
- Every CHANGELOG bullet, and every item in BACKLOG's Current Release and Next Release, is a work item with an ID, however small, including work found and done in the same pass; the only exceptions are a release result (`REL: vN.N.NN (NNN) passed ...`) and an old audit line (`CHG: WIP|1.1|BACKLOG ...`), which is no longer written: report a change to Current Release in the reply instead. Give the ID when the bullet is written, not at commit time. `test/unit/changelog_ids_test.dart` enforces it (2026-11-02: nine items in builds 555 to 558 shipped without one).
- Before every commit that changes Dart code, check each new or changed function against SonarCloud's rules and fix it first: cognitive complexity at most 15, at most 7 parameters, no string literal three or more times. SonarCloud only sees what is pushed, so a local commit is the last point it can be caught cheaply (2026-11-01: 7 new issues first seen on PR #63 moved the release to another build). A dev-to-main PR is merged only at zero new Sonar issues, not just a passing quality gate: read them with `curl -s "https://sonarcloud.io/api/issues/search?componentKeys=ExponentiallyDigital_cfg-pia-wg&pullRequest=<n>&resolved=false"`.
- `dev` can gain commits you didn't make: Andrew's merges of bot PRs. Fetch and fast-forward `dev` before starting work and before every commit.
- After every commit, and after every release (a dev-to-main merge and its tag), the next CHANGELOG release block must be open and `pubspec.yaml`'s `version:` must match it: [CHANGE-PROCESS.md](CHANGE-PROCESS.md) section 8, step 4. Check at the start of any work.
- Follow every documented rule and instruction, every time, and complete all the work that is required and asked for. If one is unclear, or two conflict, ask Andrew; never assume (Andrew, 2026-11-23, after a release plan split build 591 into two builds and left out the play block that CHANGE-PROCESS.md section 8 requires).
- When something fails or behaves unexpectedly, work out the root cause by thinking it through, and propose the root-cause fix first; never propose workarounds first, and don't read a tool's source code in place of the analysis (Andrew, 2026-11-23, when saving TESTING.md rewrote its contents and workarounds were proposed before the cause was reasoned out).
- Run the full `flutter test` before pushing to CI, starting a dry run, or committing; a dry run costs 10 minutes or more (Andrew, 2026-11-23, when three test failures that a local run would have caught cost a wasted dry run of build 591).
- Never put Dart or Python code containing backslashes, `\n` or apostrophes in a bash heredoc, since it collapses the escapes and breaks the code; write the file with the Write tool and run it (Andrew, 2026-11-23, after this broke test files and patches at least five times).
- Don't ask Andrew something already said in the conversation or recorded in the files: look it up first (Andrew, 2026-11-23, when an App Store question was asked after he had said last night's build was on TestFlight).
- Report a failed command as its error text, and give a cause only once it has been shown; never guess it (Andrew, 2026-11-23, when a push error was reported as the G: drive being unreachable, and it was not).
- `scripts/check-bash-rules.sh` enforces the heredoc, full-tests and commit-step rules above by Claude Code hook, and puts the others in front of Claude with every request (ID-691); a command it denies is not to be worked around, but done as it says.
